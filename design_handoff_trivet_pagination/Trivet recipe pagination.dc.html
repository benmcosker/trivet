Recipes · pagination

Flipping through the box

A recipe box is a thing you flip through, not a feed you fall down. This specifies numbered pages of 24, held in the URL beside the search, tag and sort parameters that are already there.
Found while reading
The library is already paginated, by accident. searchRecipeIds defaults to limit: 50 and RecipesPage passes none, so the 51st dish is invisible and nothing on the page says so — while the eyebrow directly above the grid counts the whole box from countRecipes. A household with 60 recipes is told it has 60 and shown 50. That makes this a correctness fix with a design attached, and it sets the first requirement: the page must never show fewer dishes than it claims without saying so.

Why numbers and not a feed
A box has a depth you can feel. Seven pages tells you the size of the thing you are browsing, which an endlessly extending column deliberately hides. It also means "it was about halfway down page three" is a real memory rather than a scroll position lost on reload.
Why it looks like this
MUI's Pagination is a row of circular buttons, which is a row of eight radiused objects on a page that has none. These are text on paper, and the current page carries the same 2px clay underline as the active nav item and today in the planner. Third use of one device.
The range line
Serif italic, under the control rather than beside it. It is the sentence that makes the eyebrow's count honest: 163 dishes in the box, these 24 on the page. It is also the only element here that changes when a filter is applied.

03

The mechanism

Offset, not a cursor. The query layer already takes limit and offset, so the whole of §3 is wiring rather than new SQL.

Offset — chosen
Works identically across all four sort orders, including rating, whose ordering is three columns deep with nulls last. Gives a total, which is what makes "page 3 of 7" and the range line possible. Deep offsets are slow on large tables; a shared recipe box is not a large table.
Keyset — rejected
A cursor on rating needs a composite of average, review count and createdAt, and one on search results needs ts_rank — a float nobody should be putting in a URL. It also cannot count, so it can only ever offer "more", never "of 163".
Concern
Rule
Reasoning
URL
?page=3
One-indexed, alongside q, tag and sort. Omitted entirely on page 1, so the library's canonical URL stays /recipes. Parsed like parseSort: anything unrecognised falls back rather than throwing, because it arrives from a URL where a typo is ordinary.
Page size
24
Divides by 1, 2 and 3, so no breakpoint ends on a widowed card: 24 rows on a phone, 12 at sm, 8 at md. Roughly three screens of scrolling at desktop, which is enough to be worth paginating and short enough to reach the control.
The hero
Counts as one
Page 1 while browsing is hero + 23 grid cards, not hero + 24 — otherwise page 1 holds 25 dishes and every range after it is off by one. The existing browsing flag already means the hero never appears on a searched, filtered or re-sorted page, so pages 2+ are a plain 24.
The total
countSearchRecipes
New. countRecipes counts the whole box and is right for the eyebrow; the range line needs the count of this search, under the same visibility rule and the same tag and query filters. Same WHERE clause as the search, no ORDER BY, no rating join.
Out of range
Clamp, and say so
Show the last page with a paper note above the grid. Not a 404: the recipes exist and the visitor did nothing wrong. Not a redirect: that rewrites history and breaks the back button. ?page=0 and ?page=-4 clamp to 1 silently, having no story to tell.
Position
Top of the grid
A page change lands at the first card, not at the control that caused it and not at the top of the header — the search field and collections row do not need re-reading. Server-rendered navigation does this for free; do not add scroll handling.
Photos
priority on page 1 only
The hero's photo is the only eager one, and the hero only exists on page 1. On pages 2+ the first row is above the fold and should take priority instead — three cards, not the twenty-four below them.
Mobile
Prev / Next only
Seven numbers at a 44px touch target do not fit 393px. Below sm the window collapses to two full-width targets with "Page 2 of 7" between them, and the range line stays.
04

Considered and not chosen

Show more, appending
Show 24 more
The closest runner-up, and the right answer if the box were a feed. Rejected because the state it creates cannot be linked: send someone "the fourth one down after I hit show more twice" and they get page one. It also grows the DOM without bound, and the recipe grid is photographs.
Infinite scroll
— loading —
Wrong for a library you own. Infinite scroll suits material you have not seen before and will not look for again; a recipe box is a fixed set of things you are trying to find one of. It would also put the footer's policy links permanently out of reach, and those are there for a compliance reason.
Raise the limit and move on
limit: 200
Honest about the scale of a private beta, and worth saying out loud: it fixes the truncation bug in one line. Rejected as a destination rather than a stopgap — 200 hydrated recipes with ingredients, tags and review aggregates is a heavy page, and the cap only moves the same silent cliff further out.
05

Claude Code brief

Step 3 contains the bug fix and can ship on its own. Everything else is the design around it.

1
src/lib/recipes.ts
Add countSearchRecipes(options) beside countRecipes — the search's WHERE clause, no ordering, no rating join. Extract the visibility, query and tag predicates into shared values so the search and the count cannot drift apart; a count that disagrees with the grid is worse than no count.
2
src/lib/recipe-page.ts — new
Sibling of recipe-sort.ts, for the reason that file already states: the control is a client component and must not import a module that touches Prisma. Exports PAGE_SIZE = 24, parsePage(value), and pageWindow(current, total) returning the numbers and ellipsis positions — so the window logic is testable without a DOM.
3
src/app/recipes/page.tsx
Read page from searchParams; add countSearchRecipes to the existing Promise.all; pass limit and offset to searchRecipes — the absent argument is the bug. Page 1 while browsing takes 24 and spends one on the hero; clamp an over-range page to the last and set a flag for the note.
4
src/components/RecipePagination.tsx — new
The control from §1 and §2. Links, not buttons — every page is a URL, so middle-click and open-in-new-tab work. Preserve q, tag and sort; omit page from the page-1 href. aria-current="page" on the current number, as the nav and week tabs already do. Prev and Next stay in place as inert text at the ends rather than disappearing, so the row never changes width.
5
src/components/RecipeGridCard.tsx
Accept a priority prop and pass it to RecipePhoto; the page sets it on the first three cards when there is no hero. RecipePhoto's own comment says everything below the fold stays lazy — on page 2 the first row is not below the fold.
6
src/components/RecipeSearchBar.tsx, RecipeFilters.tsx
Every control that changes what is being searched must drop page from the URL it builds. Landing on page 4 of a new two-page search is the classic bug in this pattern, and these two are the only places it can happen.
Also true
The same silent ceiling applies to plan/page.tsx, which fills the planner's recipe picker from the same shared library. It needs a different fix — a picker wants a search field, not pages — but it is the same cliff, and past the cap a dish you own becomes unplannable. Worth taking next.
